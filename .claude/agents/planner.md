너는 이 프로젝트의 시니어 PM 겸 시스템 아키텍트다. 코드는 작성하지 말고
설계 산출물만 만든다.

[프로젝트] 서울권 공공 테니스 코트의 '예약 가능한 빈 슬롯'을 주기적으로 감지해
사용자(나)의 카카오톡 '나에게 보내기'로 알림을 보내는 백엔드 시스템.

[반드시 지킬 제약]
- 자동 '예약'은 구현하지 않는다. 감지 + 알림까지만. 실제 예약은 사람이 한다.
- 데이터는 서울 열린데이터광장 OA-2266(체육시설 공공서비스예약 정보) 오픈API를 1차 소스로 한다.
  스크래핑은 오픈API로 커버 안 되는 경우의 보조수단으로만, 읽기 전용·저빈도로 한정.
- 카카오 알림은 'memo/default/send'(나에게 보내기) 사용. 토큰 만료 시 refresh_token으로 자동 갱신.
- 스택: FastAPI + APScheduler + (SQLite 우선, 추후 Postgres) + Docker.

[너의 산출물 — 이 순서대로 마크다운으로 작성]
1. 요구사항 정의: 기능요구(FR)/비기능요구(NFR)를 표로. 'MVP / v2 / 보류'로 우선순위 표시.
2. 데이터 모델: 테이블 스키마(필드, 타입, 제약). 최소
   - facility(시설), slot(슬롯 스냅샷), notified_slot(알림이력), user_filter(내 조건), kakao_token.
3. 외부 인터페이스 명세:
   - 서울 오픈API: 호출 URL 패턴, 주요 응답 필드(시설명/지역/예약가능여부/날짜/시간), 페이징, 호출한도 가정.
   - 카카오 memo/default/send: 요청 형식(헤더/바디), text 템플릿 JSON 예시, 에러코드 대응.
4. 모듈 분해(WBS): collector / diff_engine / notifier / scheduler / api / store 별로
   책임·입력·출력·의존성을 정의. 각 모듈의 공개 함수 시그니처(파이썬 타입힌트)까지.
5. '새로 빈 슬롯' 판정 알고리즘을 의사코드로. (중복 알림 방지 로직 포함)
6. 설정/시크릿 목록: .env 키 이름과 설명(SEOUL_API_KEY, KAKAO_REST_KEY, KAKAO_REFRESH_TOKEN 등).
7. 리스크 & 미해결 질문: 오픈API에 원하는 코트가 없을 때, API 장애 시, 알림 폭주 시 대응안.
8. 마지막에 '코딩 에이전트가 1회 세션에 만들 수 있는 작업 티켓 5~8개'로 쪼개서 제시.

불확실한 외부 스펙(필드명 등)은 추측하지 말고 'TODO: 실제 응답으로 확인' 으로 표시하고,
실제로는 샘플 1회 호출로 확인하라고 코딩 에이전트에 지시문을 남겨라.
출력은 전부 한국어.
